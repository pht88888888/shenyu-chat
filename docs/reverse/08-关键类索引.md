# 关键类与模型索引（从 dex 的 kotlinx.serialization descriptor 还原）

> 来源：jadx 反编译产物里类名字符串（2827 个 `com.deepseek.chat.*` 全限定名）。
> R8 把类重命名成 `defpackage.xxx`，但 serialization descriptor 里的全限定名是明文，可以直接读出官方模块划分。

## 1. 对话补全请求（网络层真实字段）

`com.deepseek.chat.network.chat.model.chat.ChatFullCompletionRequest`

```
chat_session_id
parent_message_id
prompt
ref_file_ids
thinking_enabled
search_enabled
audio_id
preempt
model_type
action
shumei_device_id
```

> 注意：网络层没有 `model` / `stream` / `temperature` 字段，模型用 `model_type` 表达，
> 流的开关由 URL 决定（`/chat/completion` 恒为 SSE）。`shumei_device_id` 是第三方风控标识。

## 2. SSE 事件模型 `domain.chat.model.completion.event`

| 类 | 含义 |
|---|---|
| `ChatCompletionReadyEventData` | 流就绪 |
| `ChatCompletionUpdateSessionEventData` | 会话信息更新（标题等） |
| `ChatCompletionUpdateParentMessageEventData` | 父消息更新 |
| `ChatCompletionTitleEventData` | 自动起标题 |
| `ChatCompletionToastEventData` + `ChatCompletionToastType` | 服务端下发的提示 |

| `ChatCompletionCheckClientUpdateEventData` | 强制/建议客户端升级 |
| `ChatCompletionAutoTtsCapabilityData` + `AutoTtsCapabilityStatus` | 自动朗读能力开关 |

## 3. 消息片段模型 `completion.message.fragments`

官方一条助手消息由**动态片段列表**拼成（`ChatFragmentList` / `DynamicChatMessageFragment`），
每种片段有自己的状态机：

| 片段 | 字段 | 对应 UI |
|---|---|---|
| `ThinkFragment` | `elapsedSeconds` | 思考块「已思考（用时 N 秒）」 |
| `SearchFragment` | `queries`、`results`、`status`、`tipContent` | 搜索块与来源列表 |
| `ToolFindFragment` | `content`、`status` | 「正在查找“…”」 |
| `ToolOpenFragment` | `content`、`reference`、`result`、`status` | 「正在浏览网页 / 正在阅读」 |
| `ReadLinkFragment` | `status` | 链接阅读状态 |
| `RequestFragment` / `ResponseFragment` | — | 用户提问 / 助手回答的静态部分 |

这解释了为什么操作条上「已思考（用时 N 秒）」「已阅读 N 个网页」这些文案能精确到秒/个数：
它们都是片段自带的字段，不是客户端估算。

## 5. 与我们实现的对应

| 官方 | shenyu-chat |
|---|---|
| `ChatFullCompletionRequest` | `net/ChatClient` 的 `/anthropic/v1/messages` 请求体 |
| SSE 事件 | `net/SseClient` 按 `anthropic` 的 `content_block_delta` 解析 |
| `ChatFragmentList` | `Message.blocks: List<Block>`（目前只有 `Block.Text` / `Block.Thinking` / `Block.Search`） |
| `ThinkFragment.elapsedSeconds` | `Block.Thinking.seconds` + `done` |
| `SearchFragment.results` | `Block.Search.hits: List<SearchHit>`（title / url / snippet / date / siteName / siteIcon） |
| `AppChatFile` | `Attachment` |

> 差距：官方的 `ToolFindFragment` / `ToolOpenFragment`（「正在查找…」「正在浏览网页」）我们还没有对应 Block，
> 自建 API 也不返回这类事件，所以 UI 上少了这两类过程提示。

> 结论：我们的 `Block` 抽象与官方 `fragment` 模型是一一对应的，只是字段名和事件协议不同；
> 如果以后要接官方网关，只需把 SSE 事件翻译成 `Block`，UI 层不用动。
